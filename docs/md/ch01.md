# 1  概述

## 1.1 项目背景

近年来，校园文创产品从“校庆纪念品”扩展为常态化业务：院系迎新、社团活动、校友返校、招生宣传都会提出定制需求，学校文创工作室（或后勤下属文创中心）需要承接“需求确认—设计打样—批量制作—入库交付”的全过程。这类业务的生产组织方式与传统制造业高度相似：产品有确定的物料构成（BOM），物料编码需要唯一，每批定制要以工单形式下达并跟踪完工，交付前要按批次入库。

但在实际走访中，工作室的生产管理仍停留在“Excel + 微信群”的阶段，暴露出三个具体问题：

- 编码靠人工编排。设计员按照“CW-徽章-001”之类的临时规则编号，不同人编出的编码风格不一致，历史编码重复的情况时有发生，物料与产品难以对应。
- BOM 靠记忆与口头传递。一件帆布包要几种布料、几克油墨，只写在师傅的便签上，新人接手容易漏料、错料。
- 工单靠聊天记录跟踪。哪天下了多少件、做完没有、入库多少，需要翻聊天记录逐条核对，无法回答“这批徽章还差多少件”。

本课程“课题一 MES 管理系统”要求以产品、物料、BOM、编码规则、工单为主线实现一套生产管理系统，并明确“每组找一个身边的例子”。本项目选择**校园文创产品生产**作为业务场景：它规模小、流程清晰、贴近学生生活，同时完整具备“产品—物料—BOM—工单”的制造业结构，能够在不虚构业务的前提下覆盖课题的全部硬性要求。

## 1.2 项目目标

本项目的总体目标是：基于赛意 IIDP 模型驱动平台，构建一个可运行、可演示的校园文创产品生产管理系统，使工作室的主数据、编码与生产工单在同一系统中闭环管理。具体目标分解为四项：

1. **主数据统一**：建立文创产品与物料两张主数据表，产品包含名称与规格，物料包含名称、规格、单位，且物料编码全局唯一。
2. **BOM 结构化**：以“产品 BOM 明细”表达每件产品的物料构成与用量，支持在产品表单的 BOM 标签页内新增、修改、删除明细。
3. **编码规则化**：编码规则可配置（前缀、日期格式、流水号位数、分隔符），由后端服务按规则统一生成编码，产品、物料、工单的编码都调用同一服务，杜绝人工编号。
4. **生产可跟踪**：以工单承载“某产品、多少件、何时完工”，工单具备草稿、已下达、已完工等状态，支持按状态查询生产进度。

在交付形态上，系统按业务域拆分为三个独立 APP（cw-base、cw-prod、cw-sys），分别承载主数据、生产与系统配置，满足课题“按模块拆分 APP”的要求。

## 1.3 系统范围界定

为避免范围蔓延，本项目对系统边界作如下界定。

| 范围 | 内容 |
| --- | --- |
| 范围内 | 文创产品与物料主数据维护；产品 BOM 明细维护；编码规则配置与编码生成服务；生产工单的创建、下达、完工与查询；角色与菜单授权；按业务域拆分 APP |
| 范围外 | 线上商城、下单与支付、物流发货、客户评价；设计稿文件与图片管理；物料采购与供应商管理；库存数量台账与成本核算；移动端 APP 打包发布；多工厂/多租户数据隔离 |

范围外的内容并非没有价值，而是与本项目“把产品做出来”的核心命题无关，且在两周的课程周期内会显著挤压主流程的完成度。相关取舍在第 2.8 节的需求裁剪中再次确认。

## 1.4 术语与缩略语

| 术语/缩略语 | 说明 |
| --- | --- |
| IIDP | 赛意工业互联网开发平台（Industrial Internet Development Platform），本项目所基于的模型驱动低代码平台 |
| APP | IIDP 中的应用单元，一个 APP 对应一个可独立部署的 jar 包，内含模型、视图、菜单与服务 |
| 模型（Model） | 对业务实体的元数据描述，一个模型对应一张数据表，通过 Java 注解声明字段与约束 |
| 视图（View） | 描述页面结构的 JSON 元数据，分为列表（grid）、表单（form）、查询（search）三类 |
| BOM | 物料清单（Bill of Materials），描述一件产品由哪些物料、各用多少构成 |
| SKU | 最小库存单位，本项目中等同于“产品 + 规格”的一个具体型号 |
| 编码规则 | 由前缀、日期格式、分隔符、流水号位数四段构成的编码模板 |
| 元数据 | 描述模型、视图、菜单、服务的数据，存放于 APP 的 jar 包中，由引擎在启动时加载注册 |
| EDGE | 引擎的元数据存储模式之一，本地从 apps/modules 下的 jar 包解析元数据 |
