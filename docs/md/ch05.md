# 5  详细设计

## 5.1 设计概述

详细设计在概要设计的六个实体基础上展开，回答三个问题：类怎么写、表怎么建、关键流程怎么走。设计遵循“数据约束下沉到模型、业务规则上浮到服务”的原则——能靠注解表达的唯一性、非空、取值范围都写在模型里，需要跨表判断的规则（如编码取号、工单状态迁移）写在服务里。

本章给出类图、六张表的字段设计、编码生成的时序图、BOM 维护的活动图、工单的状态图，以及服务接口与权限矩阵。

## 5.2 类设计

系统的业务类全部继承引擎的 `BaseModel`，通过注解声明为模型；`BaseModel` 负责提供 `get/set` 的通用存取、逻辑删除与审计字段。类图如图 5-1 所示。

![图 5-1  业务模型类图](figs/fig5-1_class.png){width=13.3cm}

类设计有三点需要说明：

1. **Product 聚合 ProductBom**。产品与 BOM 明细是一对多，`Product` 中以 `@OneToMany` 声明 `List<ProductBom> productBomList`，平台表单渲染该字段时会自动生成“标签页 + 子表”的结构，子表的新增、删除、修改随主表一起提交。
2. **ProductBom 持有两个外键**。`product` 与 `material` 都是 `@ManyToOne`，BOM 行本身不冗余存名称，展示时由引擎按外键关联取值，避免产品改名后 BOM 显示旧名。
3. **WorkOrder 对产品用弱引用**。工单在 cw-prod 中，产品在 cw-base 中，两个 APP 由不同类加载器加载。若 `WorkOrder` 直接 `import Product`，运行期会抛 `ClassNotFoundException`。因此字段声明为 `@ManyToOne(targetModel = "product") BaseModel product`，由引擎按模型名在全局元数据中解析目标模型。

## 5.4 编码生成的详细设计

编码由“前缀 + 日期段 + 分隔符 + 定长流水号”四段组成，例如规则 `prefix=WO`、`date_format=yyyyMMdd`、`separator=-`、`seq_length=4` 在 2026 年 11 月 15 日生成的第一张工单号为 `WO20261115-0001`。

生成过程如图 5-2 所示。

![图 5-2  编码生成时序图](figs/fig5-2_seq_code.png){width=13.1cm}

时序图中的关键步骤有四个：

1. **校验规则可用**。按 `rule_code` 查询规则，若不存在或 `enabled=0` 直接抛业务异常，前端提示“编码规则未配置或已停用”，避免生成无前缀的脏编码。
2. **计算日期段**。用规则的 `date_format` 格式化当前时间得到 `date_seg`。日期格式同时是流水重置的边界：格式为 `yyyyMMdd` 则每天重新从 1 开始，为 `yyyyMM` 则每月重置。
3. **锁行取号**。按 `(rule_code, date_seg)` 查询流水行并加排他锁（`SELECT ... FOR UPDATE`），行不存在则插入 `curr_value = 1`，存在则 `curr_value + 1` 后写回。锁的作用范围只在这一行，不同规则、不同日期段之间互不阻塞。
4. **拼装编码**。流水号左补零到 `seq_length` 位，按“前缀 + 日期段 + 分隔符 + 流水”的顺序拼接。若流水号超出位数（如第 10000 号、位数 4），则不再补零而直接使用实际数字，并在日志中记录提示。

取号服务的核心实现如下（节选）：

```java
@MethodService(name = "generate", displayName = "生成编码", auth = "create")
public String generate(RecordSet rs, String ruleCode) {
    CodeRule rule = queryEnabledRule(ruleCode);            // 1 校验规则
    String dateSeg = formatDate(rule.getDateFormat());     // 2 日期段
    CodeSeq seq = lockSeq(rule.getRuleCode(), dateSeg);    // 3 FOR UPDATE 取行
    int next = (seq == null) ? 1 : seq.getCurrValue() + 1;
    if (seq == null) {
        insertSeq(rule.getRuleCode(), dateSeg, next);
    } else {
        updateSeq(seq, next);
    }
    return rule.getPrefix() + dateSeg                     // 4 拼装
         + nullToEmpty(rule.getSeparator())
         + String.format("%0" + rule.getSeqLength() + "d", next);
}
```

`preview` 方法与 `generate` 共用前三步，只是不写库，用于在规则表单上“试算”下一个编码，方便管理员确认格式后再启用。

## 5.5 产品 BOM 维护流程

BOM 维护有三个入口：新建产品时一并录入、编辑产品时增删明细、复制已有产品后微调。三者最终都走“产品表单整体保存”这一条路径，活动图如图 5-3 所示。

![图 5-3  产品 BOM 维护活动图](figs/fig5-3_activity.png){width=12.7cm}

流程中的四个判断点对应四条业务规则：

- **产品名称与规格非空**：由模型上的 `@Validate.NotBlank` 拦截，前端直接标红，不进入保存逻辑。
- **BOM 至少一行**：产品必须有构成，否则工单无法领料；保存时若明细为空则提示“请至少添加一行 BOM”。
- **用量为正整数**：`amount` 为 0 或负数时提示“用量必须大于 0”，避免出现零耗用。
- **同产品同物料不重复**：保存前按 `material_id` 分组检查，重复时定位到具体行并提示“物料 XX 已存在，请修改用量”。

校验通过后，平台在一个事务内先写主表、再按明细的增删改情况写子表，任一环节失败整体回滚，保证不会出现“产品保存了但 BOM 只存了一半”的中间态。

## 5.6 生产工单的状态设计

工单只有三个状态，但状态之间的迁移必须受控，否则会出现“已完工的工单又被下达”这类脏数据。状态图如图 5-4 所示，迁移规则见表 5-7。

![图 5-4  生产工单状态图](figs/fig5-4_state.png){width=12.5cm}

**表 5-7 工单状态迁移表**

| 当前状态 | 操作 | 目标状态 | 前置条件 | 后置动作 |
| --- | --- | --- | --- | --- |
| 1 草稿 | 保存 | 1 草稿 | 产品、数量、日期齐全 | 无 |
| 1 草稿 | 下达 | 2 已下达 | BOM 至少一行 | 记录下达时间与操作人 |
| 2 已下达 | 完工 | 3 已完工 | 实际完工数量 > 0 且不超过计划数量 | 记录完工时间，工单转只读 |
| 2 已下达 | 撤回 | 1 草稿 | 尚未报完工 | 清空下达时间 |
| 3 已完工 | —— | —— | 不允许任何迁移 | 只能查看 |

状态迁移由服务方法 `workOrderService.changeStatus` 统一入口处理，不通过直接修改 `status` 字段实现，这样所有迁移都会经过同一处校验与日志记录。

## 5.7 服务接口设计

系统对外提供的服务共 8 个，均由 `@Service` 标注的类以 `@MethodService` 暴露，同时在对应的 `@Model` 类上保留同名委托方法——引擎的 `ServiceLoader` 只扫描模型类上的注解，这是实测结论。接口清单见表 5-8。

**表 5-8 服务接口清单**

| 服务 | 方法 | 入参 | 返回 | 权限 | 说明 |
| --- | --- | --- | --- | --- | --- |
| codeRuleService | generate | ruleCode | String | create | 按规则生成并占用一个编码 |
| codeRuleService | preview | ruleCode | String | read | 预览下一个编码，不占用 |
| productService | createWithCode | name、spec、status | Product | create | 新增产品，编码由 cw-sys 生成 |
| productService | addBom | productCode、materialCode、amount | ProductBom | update | 追加 BOM 明细，校验用量与重复 |
| productService | checkBom | productCode | Map | read | 返回 BOM 行数与校验结论 |
| materialService | createWithCode | name、spec、unit | Material | create | 新增物料，物料编码唯一 |
| workOrderService | createWithCode | productId、planQty、planDate | WorkOrder | create | 新建工单，状态固定为草稿 |
| workOrderService | changeStatus | code、target | Map | update | 工单下达、撤回、完工的统一入口 |

接口设计上有意保持“薄”：服务只做业务编排与校验，查询仍走平台的通用接口，这样既减少重复代码，也保证视图、接口、数据三者对同一模型的行为一致。之所以连新增也要写自定义服务，是因为本机引擎版本的标准 `create` 服务取不到记录列表（见 6.8 难点五），查询类服务则继续复用平台实现。

编码生成与业务新增的关系值得单独说明：`cw-base` 与 `cw-prod` 都不直接依赖 `cw-sys` 的模型类（跨 APP 类加载会找不到类），而是各自持有一份 `CodeGenFacade`，用原生 SQL 对 `cw_code_rule` 与 `cw_code_seq` 取号。两份实现共用同一对表和同一条流水，因此产品编码、物料编码、工单编码在同一序列上递增、互不重号。

## 5.8 权限设计

权限采用“角色—菜单—按钮”三级控制，全部在平台的权限中心配置，业务代码不做角色判断。四个角色的权限矩阵见表 5-9，其中“—”表示无权限，“只读”表示可查询不可改。

**表 5-9 角色权限矩阵**

| 功能 | 文创设计员 | 生产主管 | 仓库管理员 | 系统管理员 |
| --- | --- | --- | --- | --- |
| 产品管理 | 读写 | 只读 | — | 只读 |
| 产品 BOM | 读写 | 只读 | — | 只读 |
| 物料管理 | 只读 | 只读 | 读写 | 只读 |
| 生产工单 | — | 读写 | 只读 | 只读 |
| 编码规则 | — | — | — | 读写 |
| 编码流水 | — | — | — | 只读 |
| 角色与菜单授权 | — | — | — | 读写 |

矩阵中的“只读”通过菜单权限下发，“读写”额外授予按钮权限（`create`、`update`、`delete`）。这样即使有人手工拼出接口地址，缺少按钮权限的请求也会被引擎拒绝。

## 5.9 校验规则与提示语

校验分三层：模型注解层、服务校验层、数据库约束层。三层中任何一层拦截都给出统一格式的中文提示，避免出现英文异常堆栈。主要校验点见表 5-10。

**表 5-10 主要校验点与提示语**

| 校验层 | 校验点 | 触发时机 | 提示语 |
| --- | --- | --- | --- |
| 模型注解 | 产品名称非空 | 保存产品 | 产品名称不能为空！ |
| 模型注解 | 物料编码非空 | 保存物料 | 物料编码不能为空！ |
| 模型注解 | 规则前缀非空 | 保存规则 | 编码前缀不能为空！ |
| 服务 | BOM 至少一行 | 保存产品 | 请至少添加一行 BOM 明细 |
| 服务 | 用量大于 0 | 保存 BOM 行 | 第 N 行用量必须大于 0 |
| 服务 | 同产品同物料唯一 | 保存 BOM 行 | 物料「XX」已存在，请修改用量 |
| 服务 | 规则存在且启用 | 生成编码 | 编码规则未配置或已停用 |
| 服务 | 工单数量不大于计划 | 工单完工 | 完工数量不能大于计划数量 |
| 数据库 | 编码唯一 | 并发写入 | 编码冲突，请重试（服务自动重试至多 5 次） |

## 5.10 界面设计说明

界面全部由视图 JSON 渲染，本节只说明三类页面的设计要点，页面截图见第 6 章。

**列表页**以“编码、名称、关键状态”为主列，宽度按内容分配；顶部工具栏提供新建、批量删除，行内提供查看、编辑。列表默认按创建时间倒序，状态列用颜色区分（在售绿、打样蓝、停产灰）。

**表单页**左侧为基本信息，右侧或下方为关联信息。产品表单把 BOM 明细放在“BOM 清单”标签页，标签页上显示明细条数；工单表单把状态相关的操作按钮放在底部，草稿状态显示“下达”，已下达显示“报完工”。

**查询页**只放高频条件（名称、编码、状态、日期区间），不做“高级查询”面板，避免首屏信息过载。查询条件与列表列一一对应，便于用户理解过滤结果。
