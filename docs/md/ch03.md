# 3  可行性分析

本章从经济、技术、进度与组织、法律与合规四个方面论证项目是否值得做、能不能做完。判断标准不是“理论上可行”，而是“在两周、单人、本机环境的约束下能否交付一个可演示、可写文档的成品”。

## 3.1 经济可行性

项目不采购任何商业软件与云资源，全部运行在开发者本人的笔记本上；平台、数据库、缓存与 Web 服务器均为课程提供的教学版本或开源软件。成本构成如下。

| 成本项 | 说明 | 金额（元） |
| --- | --- | --- |
| 人力成本 | 1 人 × 14 天 × 6 小时，按学生实习折算 20 元/小时 | 1680 |
| 平台与中间件 | IIDP 引擎 v3.0.1（课程教学授权）、MySQL、Redis、nginx 均为已有或开源 | 0 |
| 硬件 | 使用现有笔记本（i5/16G/512G），无需新购 | 0 |
| 云资源 | 不部署公网，本机回环地址演示 | 0 |
| 打印与装订 | 开发文档、中期材料打印装订 | 40 |
| 合计 | —— | 约 1720 |

收益方面，系统替代现有 Excel 台账后，可直接消除两类返工：一是编码重复导致的单据对不上，按每月 4 次、每次核对 1 小时计，每月节省 4 小时；二是 BOM 漏料导致的中途补料，按每月 2 次、每次 2 小时计，每月节省 4 小时。按 20 元/小时折算，年化收益约 1920 元，与投入基本持平。需要说明的是，本项目的经济价值主要是**教学与流程规范价值**，而非直接的经济回报；在可行性判断上，投入金额小、无需额外采购，是“可以做”的充分条件。

## 3.2 技术可行性

平台能力与本项目需求的对应关系如下表。可以看出，除编码规则外，其余需求都能由平台既有能力直接承载，不需要从零搭建框架。

| 平台能力 | 具体表现 | 支撑的需求 |
| --- | --- | --- |
| 模型定义 | 以 Java 注解声明模型与字段，引擎自动建表并生成元数据 | F01、F02、F10 |
| 主子表关系 | `@OneToMany` / `@ManyToOne` 表达产品与 BOM 明细的一对多关系 | F03、F04 |
| 视图元数据 | JSON 描述列表、表单、查询三类页面，表单可挂标签页承载子表 | F01—F05、F10 |
| 服务扩展 | `@Service` + `@MethodService` 声明服务方法，随 APP 一起加载 | F06、F07、F12 |
| 权限中心 | 角色、菜单、按钮三级授权，视图按钮可直接绑定权限码 | F13 |
| APP 打包 | Maven 插件把模型、视图、菜单打进 jar，放入 apps/modules 即注册 | F09、F14 |

技术上真正需要攻克的只有三处，均已有明确对策：

1. **编码并发生成**。参考程序中的编码工具使用静态计数器，重启即失效，无法支撑“按规则生成”。对策是新增“编码规则表 + 流水号表”，以“规则标识 + 日期段”为唯一键，取号时用 `SELECT ... FOR UPDATE` 锁行，保证并发下不重号；规则变更只影响后续编码，历史编码不变。
2. **BOM 主子表联动**。产品与 BOM 明细是一对多关系，表单需要在同一页面内维护子表。对策是采用平台表单的标签页 + 子表编辑模式，子表的新增、删除以行操作提交，保存时整体落库，避免半成品数据。
3. **元数据注册模式**。引擎以 EDGE 模式从 jar 解析元数据，配置不当会出现“模型已建表但菜单不显示”。对策是严格按参考程序的目录结构组织 `app.json`、`views` 与 `menus.json`，并先以单个模型打通链路，再批量复制。

团队技术储备方面，开发者已完成课程 5 天实训（系统认知、数据建模、ORM、服务扩展、APP 打包），具备 Java 8 与 SQL 基础；平台的学习曲线集中在“注解写法”与“视图 JSON 结构”，参考程序已提供完整样例，属于可复制的知识。

## 3.3 进度与组织可行性

项目自 2026 年 11 月 15 日启动，11 月 29 日截止，共 14 个自然日。按增量原型思路拆为六个阶段，每个阶段都要求产出可演示的增量，而不是最后一次性集成。

| 阶段 | 时间 | 工作内容 | 产出 |
| --- | --- | --- | --- |
| M0 环境与链路 | 11-15 至 11-16 | 编译参考工程、启动引擎与前端、跑通最小 APP（一个模型 + 三个视图） | 可登录的平台、最小 APP 页面 |
| M1 主数据 | 11-17 至 11-19 | 产品、物料模型与页面；BOM 标签页；编码字段接入 | 产品与物料可增删改查 |
| M2 编码规则 | 11-20 至 11-21 | 编码规则模型与页面；编码生成服务；并发取号验证 | 三个业务对象的编码均由服务生成 |
| M3 生产工单 | 11-22 至 11-23 | 工单模型、状态流转、用料折算 | 工单可下达、可完工 |
| M4 权限与打磨 | 11-24 至 11-25 | 四角色授权、菜单整理、必填校验与提示 | 四个账号权限正确 |
| M5 测试与交付 | 11-26 至 11-29 | 功能走查、缺陷修复、文档定稿、演示视频与 PPT | 五项提交物齐备 |

进度上的主要风险是 M0 阶段的环境问题（依赖下载、授权服务、数据库初始化）不可控。对策是：把 M0 单独作为一个里程碑，一旦超过一天未打通，立即降级为“只做 cw-base 单 APP + 两个模型”，确保有可演示的成品；文档写作与代码开发并行，不把文档留到最后三天。

## 3.4 法律与合规可行性

系统使用的 IIDP 引擎为课程提供的教学版本，APP 清单中标注的许可为 LGPL 3.0；MySQL 为 GPL 许可，Redis 为 BSD 许可，nginx 为 BSD 许可，均允许在教学与课程作业场景下免费使用。项目不分发引擎安装包，仅在本地运行，不涉及商业再分发。

数据方面，系统只录入文创产品、物料与工单信息，不采集学生个人信息、不涉及支付与身份认证数据；演示数据为自行编造的示例数据（如“校徽徽章 58mm”），不对应真实交易。文档与演示视频中出现的学校名称、工作室名称均作泛化处理。

合规上唯一需要注意的是引用规范：文档中引用平台手册与课程材料时注明来源，参考程序仅用于对齐技术栈与代码风格，业务代码为自行编写，不存在抄袭。

## 3.5 结论

综合以上四个方面：经济上投入不足两千元且无需采购，技术上平台已覆盖八成需求、剩余三处难点均有明确对策，进度上采用增量原型并设置降级方案，法律上无许可与数据风险。因此本项目**可行**，建议按第 3.3 节的六个阶段推进，优先保证 M1 与 M2 两个阶段，因为它们直接对应课题的 9 条硬性要求。
