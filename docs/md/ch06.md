## 6.3 关键实现

### 6.3.1 模型声明

模型类只做三件事：用注解描述表与字段、实现链式 setter/getter、声明关联关系。以文创产品为例：

```java
@Model(name = "product", tableName = "cw_product", description = "校园文创产品",
       displayName = "文创产品", isAutoLog = Bool.True)
public class Product extends BaseModel<Product> {

    @Validate.NotBlank(message = "产品名称不能为空！")
    @Property(displayName = "产品名称", displayForModel = true)
    private String name;

    @Property(displayName = "产品编码")
    private String code;

    @Property(displayName = "产品状态", defaultValue = "1", widget = "select", length = 256)
    @Selection(values = {
            @Option(label = "设计中", value = "1"),
            @Option(label = "打样中", value = "2"),
            @Option(label = "批量制作", value = "3"),
            @Option(label = "已入库", value = "4")
    })
    private String status;

    @OneToMany
    private List<ProductBom> productBomList;

    public Product setName(String name) { this.set("name", name); return this; }
    public String getName() { return getStr("name"); }
}
```

`@Model` 的 `tableName` 决定物理表名，`isAutoLog = Bool.True` 让引擎自动维护创建人、修改人与时间；`@Property` 中的 `widget = "select"` 与 `@Selection` 让状态字段在表单里渲染为下拉框而不是文本框；`@OneToMany` 让 BOM 明细成为产品的子表。

### 6.3.3 跨 APP 的模型引用

工单在 cw-prod，产品在 cw-base，两个 APP 由不同的类加载器加载。直接写 `import com.sie.app.cw.base.model.Product` 在编译期能通过，运行时却会因类加载隔离抛 `ClassNotFoundException`。解决办法是用模型名做弱引用：

```java
@ManyToOne(targetModel = "product")
@JoinColumn(name = "product_id")
private BaseModel product;
```

引擎在解析 `targetModel` 时按模型名到全局元数据仓库查找，因此 cw-prod 不需要在编译期依赖 cw-base 的类，打包时也不必互相引入。

### 6.3.4 编码服务与并发控制

编码服务是唯一包含业务逻辑的类，位于 cw-sys。它对外暴露两个方法：`generate` 占号并返回编码，`preview` 只算不占。核心取号逻辑如下：

```java
private int claimNextValue(CodeRule rule, String dateSeg) {
    String ruleCode = rule.getRuleCode();
    for (int attempt = 1; attempt <= MAX_RETRY; attempt++) {
        lockSeqRow(ruleCode, dateSeg);                    // SELECT ... FOR UPDATE
        CodeSeq seq = findSeq(ruleCode, dateSeg);
        if (seq == null) {
            try {
                new CodeSeq().setRuleCode(ruleCode).setDateSeg(dateSeg)
                             .setCurrValue(1).create();
                return 1;
            } catch (RuntimeException e) { continue; }     // 唯一键冲突 → 重试
        }
        int oldValue = seq.getCurrValue() == null ? 0 : seq.getCurrValue();
        int next = oldValue + 1;
        Filter casFilter = Filter.equal("ruleCode", ruleCode)
                .and(Filter.equal("dateSeg", dateSeg))
                .and(Filter.equal("currValue", oldValue)); // CAS：WHERE curr_value = 旧值
        new CodeSeq().updateByFilter(
                Collections.singletonMap("currValue", next), casFilter);
        CodeSeq current = findSeq(ruleCode, dateSeg);      // 回读校验
        if (current != null && current.getCurrValue() == next) {
            return next;
        }
    }
    throw new IllegalStateException("编码生成失败：并发冲突重试 5 次仍未成功");
}
```

取号用了三道防线，原因在于 SDK 的模型层没有暴露“影响行数”和事务句柄：

1. **行锁**：先对 `(rule_code, date_seg)` 这一行执行 `SELECT id ... FOR UPDATE`，把同规则同日期段的并发取号串行化；若因 SDK 限制拿不到锁，则降级为无锁执行，不阻断业务。
2. **条件自增 + 回读**：更新语句带上 `curr_value = 旧值` 的条件，等价于一次 CAS；由于拿不到影响行数，用“更新后回读是否等于自己写入的值”来判断本次更新是否生效。
3. **唯一索引**：`cw_code_seq` 上建 `(rule_code, date_seg)` 唯一索引，并发插入时只有一条能成功，另一条捕获异常后重试。

三道防线叠加后的效果是“宁可重试，不可重号”：正常情况下第一次就能取到号，极端并发下最坏重试 5 次后抛异常，由上层提示用户重试，而不是生成重复编码。

## 6.5 部署与启动

部署按“授权 → 引擎 → 前端”三步，四次启动的顺序不能颠倒：

1. 启动 Redis 与 MySQL，确认 6379、3306 端口可连。
2. 运行 `sie-grant/grant-dev.exe`，监听 8080，为引擎签发授权。
3. 运行 `java -jar sie-iidp-demo-start-1.0-SNAPSHOT.jar`，引擎读取 `apps/apps.json`、扫描 `apps/modules` 下的 jar、注册模型并建表，约 40 秒后监听 8061。
4. 启动 nginx（`conf/nginx.conf` 监听 30666），把 `/iidp/` 指向前端 dist，`/root/api/*` 反向代理到 8061。
5. 浏览器访问 `http://localhost:30666/iidp/`，用 `admin_000001/Admin_000001` 登录。

需要改动的配置只有三处：`dbcp.properties` 的数据库连接、`application-dev.properties` 中的 `image.minimal.requiredApps`（追加 cw 的三个 APP）与 `apps/apps.json` 的 SDK 列表。首次部署若出现“授权弹窗空白、生成视图按钮无响应”，执行一次 `sql/platform-web-app-init.sql` 中的 `UPDATE meta_app SET view_file = ...` 即可，这是课程材料中已记录的平台初始化步骤。

## 6.8 开发难点与解决过程

实现过程中真正卡住的地方有六处，记录如下，既作为过程材料，也便于后续维护。

**难点一：跨 APP 引用导致运行期类找不到。** 最初工单直接 `import Product`，编译通过但引擎启动时报 `NoClassDefFoundError`。查阅引擎的模型加载逻辑后确认两个 APP 由独立类加载器加载，改为 `@ManyToOne(targetModel = "product")` 弱引用后解决。

**难点二：自定义服务不被扫描。** 按 Spring 的习惯写了 `@Service` 注解的类，启动后服务却调不到。反编译 SDK 的 `ServiceLoader` 后发现它只遍历 `@Model` 类上的方法与注解，因此在 `CodeRule`、`Product`、`Material`、`WorkOrder` 模型类上各补了一组 `@MethodService` 委托方法，把调用转发到服务类。

**难点三：编码并发生成。** 参考程序的 `CodeGenerator` 用静态自增变量，进程重启即归零，多实例部署必然重号。第一版按“规则表 + 流水表 + CAS + 回读校验 + 重试 5 次”实现，20 线程并发实测只有 1 个成功、19 个在重试耗尽后失败——原因是 SDK 模型层的查询在同一会话内返回的是快照，重试永远读到旧值。改为用引擎的 `RelationDBAccessor` 直接执行 `SELECT ... FOR UPDATE` + `UPDATE` + `commit`，把取号放进一个事务里，并发 20 线程全部成功且号码连续，问题解决。

**难点四：关联字段的查询与写入。** 两个坑：一是 `search(filter, properties, ...)` 的 `properties` 传 `null` 时引擎拼不出 SELECT 列表，直接返回空集合，表面上像“查不到数据”；二是用 `Filter.equal("product", id)` 过滤 `@ManyToOne` 字段同样匹配不到行。对策是查询一律显式给出属性列表，涉及关联字段的过滤改为原生 SQL 按列名匹配；写入关联字段时传主键字符串而不是模型实例，否则 ORM 序列化关系对象会抛 `NotSerializableException`。

**难点五：平台自带 create 服务不可用。** 直接调用任意模型的 `create` 都抛 `NullPointerException`，反编译 `BussModelDataAccess.create` 后定位到偏移 103 处的 `aload_2; List.iterator()`——服务入口拿到的记录列表是 `null`。判断为该版本引擎在本机环境的缺陷，于是新增产品、物料、BOM、工单全部改走自定义服务，平台标准服务只用于查询。

**难点六：APP 清单混入重复 jar 导致启动崩溃。** 详见 6.9.1 末尾的记录。

## 6.9 遗留问题与后续计划

### 6.9.2 菜单为空的排查与修复

页面能打开、数据能查出，但左侧菜单一度为空。这一段完整记录排查过程，因为它是本次实作里最花时间的坑。

**现象**：`admin_000001` 登录后进得了主界面，菜单树不渲染；直接调 `sie-iidp-iam/ui_menu.loadMenu` 返回空数组，而课程自带的 `implementer` 账号同一接口返回 36 条平台菜单。

**逐层排除**：先查 `tenant_meta_mapping`，三个自研 APP 的 147 条映射（含 57 条 Menu）都在，`effective=1`、`deleted=0`，`auth_code` 形如 `cw_product_menu@Menu`；再查 `tenant_permission`，cw 的菜单权限码与 `auth_id` 也都在；又补了 48 条 `@View` 授权码、2646 条 `rbac_role_permission`、27 条 Menu 与 9 条 ProductLine 的 `tenant_function_auth`，仍不见效。把 `meta_app.view_file` 改成 `cw-base-web`、`global=1` 也不见效（已改回）。

**定位**：反编译 `UiMenu.getPermissionMenu` 后读出真实链路——`StoreMetaUtil.getAllMenu()` 取运行时菜单，`TenantPermission.selectPermissionByMetaIds` 用 `tenant_meta_mapping` 左连 `tenant_permission` 取 `auth_id`，再由 `AuthModel.getUserAuthV2` 按角色算权限位图，最后用 `UserAuthVo.getPremissAll(app, tag)` 或 `permissionBitmap.testBit(authId)` 过滤。顺着这条链查 `rbac_role_auth`，发现平台自带的 24 行都是“角色 + app_name + app_tag + `app_all=1`”的**应用级授权**，而我们三个自研 APP 一行都没有——菜单在应用级就被挡掉了，跟菜单表、视图表、发布态都无关。

**修复**：给 `admin_000001`（`rbac_role_admin`）与 `admin_000002`（`06bro028u1g0r`）各补三条 `rbac_role_auth` 记录（`app_name` 分别为 `cw-base`、`cw-prod`、`cw-sys`，`app_tag='master'`，`app_all='1'`），重新登录后 `loadMenu` 立刻返回 9 个 cw 菜单，页面正常渲染，6.6 的三张截图就是这样拍到的。

**另外两点仍需注意**：一是首次部署时 ORM 查询可能恒为空，调一次应用市场的 `refreshAllAppJson` 即可恢复（本机就是这样恢复的），但这不是标准部署步骤，换环境要留意；二是 `meta_model` 与 `meta_menu` 在本机库里没有数据，开发者中心的“模型管理”“菜单管理”页面用不了，好在应用级授权不依赖它们。
